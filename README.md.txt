# 🛡️ SentinelAI — Adaptive Time-Series Anomaly Detection

SentinelAI is a Python-based time-series anomaly detection project designed to identify unusual patterns in sequential data. It combines statistical detection techniques with an interactive dashboard to visualize suspicious observations, highlight potential anomalies, and provide interpretable detection results.

The project uses the Numenta Anomaly Benchmark (NAB) artificial time-series dataset to explore and evaluate anomaly detection.

## 🔍 Overview

Time-series data is generated by systems such as servers, applications, sensors, and infrastructure monitoring platforms. Unexpected changes in these readings can indicate unusual behavior that deserves further investigation.

SentinelAI provides a lightweight dashboard for analyzing time-series readings and identifying potential anomalies using two statistical detection methods

1. Global Z-score anomaly detection.
2. Rolling median and Median Absolute Deviation (MAD) detection.

The application combines their results to produce a unified anomaly flag and displays the findings through an interactive dashboard.

---

## 🎯 Problem Statement

The objective of SentinelAI is to develop a lightweight anomaly detection system that identifies observations or temporal windows that deviate significantly from baseline time-series behavior.

The system aims to

- Identify unusual time-series observations.
- Assign a normal or anomalous classification.
- Generate anomaly scores where implemented.
- Explain why observations are flagged.
- Visualize anomaly detection results.
- Evaluate detection performance using labeled data.

The project is developed in the context of Challenge 2 — Sentinel Adaptive Time-Series Anomaly Detection.

## 🧠 Detection Methodology

### 1. Global Z-Score Detection

The Z-score measures how far a reading is from the dataset's mean in units of standard deviation.

[
Z = frac{x-mu}{sigma}
]

Where

- (x) is the current observation.
- (mu) is the mean.
- (sigma) is the standard deviation.

Observations exceeding the configured threshold are flagged as potential anomalies.

Purpose Identify readings that differ substantially from the overall statistical baseline.

### 2. Rolling Median and MAD Detection

The rolling detector uses a local window to estimate typical behavior.

The median provides a robust measure of central tendency, while the Median Absolute Deviation (MAD) measures the spread of observations around the median.

This approach can help identify local deviations that a global baseline might overlook.

Purpose Detect unusual observations relative to recent readings.

### 3. Combined Anomaly Detection

SentinelAI combines the detector outputs using a logical OR operation.

Conceptually

```python
Combined_Anomaly = Is_Anomaly  Rolling_Anomaly
```

An observation is classified as anomalous if either detector flags it.

This approach combines global and local statistical signals. It can also increase the number of alerts, so the results should be evaluated against reliable ground-truth labels.

## 📁 Dataset

SentinelAI uses the Numenta Anomaly Benchmark (NAB) dataset.

The current example dataset is

`art_daily_jumpsup.csv`

It contains time-stamped readings representing artificial time-series behavior.

The current project dataset contains 4,032 observations.

The project also uses `combined_labels.json` to check a known anomaly timestamp

`2014-04-11 090000`

The application can check whether SentinelAI flags this labeled point.

Important The current label file contains only a known anomaly timestamp for this dataset. It does not provide complete ground-truth labels for all observations. Therefore, the known-point check alone cannot establish full-dataset Precision, Recall, or F1 performance.

The NAB dataset and its labeling methodology are available in the official repository

[Numenta Anomaly Benchmark (NAB)](httpsgithub.comnumentaNAB)

## 🔄 How It Works

The general workflow is

1. Load data Load the default dataset or upload a compatible CSV.
2. Prepare readings Interpret the time and numerical reading columns.
3. Run global detection Identify observations that deviate from the global statistical baseline.
4. Run rolling detection Compare observations with local rolling statistics.
5. Combine results Flag an observation if either detector identifies it.
6. Classify observations Assign a normal or anomalous status.
7. Visualize results Display time-series readings, alerts, and severity summaries.
8. Validate detections Compare results against known labels when available.
9. Export results Download reports using the dashboard's configured reporting functionality.

## 📏 Evaluation

The project includes an evaluation section for labeled datasets and a known-point validation check.

### Precision

Precision measures the proportion of predicted anomalies that are genuine anomalies.

[
text{Precision} = frac{TP}{TP+FP}
]

### Recall

Recall measures the proportion of actual anomalies that are detected.

[
text{Recall} = frac{TP}{TP+FN}
]

### F1 Score

The F1 score is the harmonic mean of Precision and Recall.

[
F1 = 2 times frac{Precision times Recall}{Precision + Recall}
]

Where

- TP True positives.
- FP False positives.
- FN False negatives.

These metrics require reliable ground-truth labels.

### Evaluation Status

The current implementation has confirmed detection of the known NAB anomaly timestamp. Additional validation is needed before reporting reliable full-dataset or event-based performance metrics.

The challenge also specifies two performance measurements

- Detection delay Time between true anomaly onset and detector trigger.
- Inference runtime Time required to process a streaming data window.

These should be measured and reported before claiming that all challenge evaluation requirements are satisfied.

## ⚠️ Limitations

- Statistical thresholds can produce false positives.
- Global statistics can be influenced by extreme observations.
- Rolling detection depends on its window and threshold configuration.
- Combining detectors can increase the total number of alerts.
- The current known-point validation does not provide complete ground truth.
- Event-based F1, detection delay, and per-window inference runtime require additional implementation or verification.
- The current dashboard should not be considered a production monitoring system without further testing.
